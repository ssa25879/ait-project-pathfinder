# Design

## Context

저장소에는 기획서만 있고 코드는 없다. 동기와 범위는 `proposal.md`, 요구사항은 `specs/`를 따른다.

2026-11-03에 앱인토스 공식 문서에서 확인한 제약은 다음과 같다.

- **저장:** `@apps-in-toss/web-framework`의 `Storage`는 `getItem`/`setItem`/`removeItem`/`clearItems`를 제공하는 비동기 문자열 저장소다. 토스 앱을 삭제하면 데이터도 삭제된다.
- **데이터 삭제:** 사용자는 내비게이션 바 메뉴의 "미니앱 용량 삭제"로 서비스별 데이터를 지울 수 있다.
- **출시 가이드:** 라이트 모드, 제스처 확대 비활성화, 앱인토스 내비게이션 바 사용, 최초 화면 뒤로가기 시 종료, SSR 금지, `eval` 금지, SDK 과다 호출 금지, 호출 실패 시 재시도 횟수·간격 제어를 요구한다.
- **확대 제어:** 핀치 줌은 기본으로 막혀 있지 않으며, viewport meta의 `maximum-scale=1, user-scalable=no`로 막는다.
- **구성:** `npm install @apps-in-toss/web-framework` 후 `npx ait init`을 실행한다. `appName`은 콘솔 등록 정보와 같아야 업로드할 수 있다.
- **TDS 패키지:** 연동 튜토리얼은 `@toss/tds-mobile`, `@toss/tds-mobile-ait`, `@emotion/react@^11`, `react@^18`을 설치하도록 안내한다.

## Goals / Non-Goals

**Goals:**

- 그래프·판정·일정 계산을 React와 SDK 없이 단위 테스트할 수 있게 분리한다.
- 목록, 경로도, 일정 분석이 같은 계산 결과를 쓰게 한다.
- SDK 저장소를 경계 뒤에 두어 테스트와 브라우저 개발에서 교체할 수 있게 한다.

**Non-Goals:**

- 대규모 그래프 성능 최적화. 초기 목표인 5~15개 작업을 기준으로 삼으며, 개수를 제한하지는 않는다.
- 전역 상태 관리 라이브러리, 백엔드, 계정 연동 도입.
- 콘솔 등록과 출시 심사 제출.

## Decisions

### 1. 모듈 구조

```text
src/
  domain/   model, validation, graph, readiness, schedule, layout, mutations (순수 함수)
  storage/  직렬화·버전 변환, 저장 스케줄러, SDK 어댑터
  state/    Context + useReducer, 파생 값 selector
  screens/  화면 5개
  ui/       공통 컴포넌트
```

`domain/`은 React, TDS, SDK를 import하지 않는다. 기획서 8.2의 원칙을 구조로 보장하기 위한 결정이다.

### 2. 데이터 모델

기획서 6장의 `Project`, `Task`를 그대로 쓴다. 파생 값은 저장하지 않고, 저장 형식에만 버전을 더한다.

```ts
type StoredData = { version: 1; projects: Project[]; tasks: Task[] };
```

ID는 `crypto.randomUUID`가 있으면 사용하고, 없으면 시각과 난수를 조합한다. 보안 용도가 아니므로 추가 의존성을 두지 않는다.

### 3. 저장 방식: `Storage`의 단일 키에 전체 JSON 저장

- **선택 이유:** 프로젝트 삭제와 참조 정리처럼 여러 레코드가 함께 바뀌는 변경도 한 번의 쓰기로 끝나 부분 저장 상태가 생기지 않는다. 소규모 데이터에는 전체 직렬화 비용도 작다.
- **키별 분할을 택하지 않은 이유:** 쓰기 양은 줄지만 부분 실패 시 참조가 깨질 수 있고, 그 복구 로직의 비용이 더 크다.
- **`localStorage`·IndexedDB를 택하지 않은 이유:** 공식 문서에 Origin 변경(`web.tossmini.com` → `apps.tossmini.com`)과 이를 위한 마이그레이션 API가 있어, Origin에 묶인 저장소는 이전 위험이 있다.

저장 경계는 `load(): Promise<string | null>`과 `save(value: string): Promise<void>`이며, 테스트에서는 메모리 구현으로 교체한다.

### 4. 저장 스케줄링과 데이터 보호

- 변경 후 300ms 디바운스로 쓰고, 쓰기는 한 번에 하나만 실행한다. 쓰는 중에 생긴 변경은 끝난 뒤 최신 값으로 한 번 더 쓴다.
- 실패 시 1초, 3초 간격으로 최대 2회 재시도하고, 그래도 실패하면 오류 상태로 전환해 수동 재시도를 제공한다.
- 화면이 숨겨지면(`visibilitychange`) 대기 중인 쓰기를 즉시 실행한다.
- 상태는 `loading` / `ready` / `load_error` / `newer_version`으로 나눈다. **`ready`가 아니면 저장을 호출하지 않아** 읽기 실패나 손상 시 원본을 덮어쓰지 않는다.
- 읽은 데이터는 형식과 참조 무결성을 검증한다. 순환, 교차 프로젝트 참조, 없는 ID 참조가 있으면 손상으로 처리한다.

### 5. 상태 관리: Context + `useReducer`

쓰기 동작은 모두 `domain/mutations`를 거쳐 검증을 한곳에 모은다. 파생 값은 프로젝트별로 메모이즈한 selector 하나에서 계산해 화면 간 결과가 달라지지 않게 한다. 외부 상태 라이브러리는 기획서 8.2에 따라 도입하지 않는다.

### 6. 그래프와 CPM

- 순환 판정과 위상 정렬은 Kahn 알고리즘 하나로 처리한다. 저장 후보 그래프를 만들어 정렬에 실패하면 거부하고, 안내할 순환 경로는 DFS로 찾는다.
- 위상 순서대로 ES/EF를, 역순으로 LS/LF를 계산한다. 작업 상태는 입력으로 쓰지 않는다.
- 여유 기간 0은 핵심 작업, `EF(앞) = ES(뒤)`인 핵심 작업 쌍의 연결은 핵심 연결이다. 경로를 일일이 열거하지 않으므로 복수 핵심 경로에서도 경로 수가 늘어나는 문제가 없다.
- 표시 날짜는 `시작일 + ES`로 변환한다. 종료일은 포함 기준이라 `시작일 + 총 기간 - 1`이며, 총 기간이 0이면 표시하지 않는다. 시간대 오류를 막기 위해 `YYYY-MM-DD` 문자열을 UTC 기준으로 계산한다.

### 7. 경로도: 외부 라이브러리 없이 직접 구현

- **배치:** 단계는 선행 작업까지의 최장 깊이로 정하고, 단계 안 순서는 barycenter 정렬로 교차를 줄인다. `domain/layout`의 순수 함수로 두어 테스트한다.
- **렌더링:** 노드는 절대 위치의 HTML `button`으로, 연결선은 그 아래 SVG로 그린다. 터치 영역과 글자 표시, 접근성을 기본 동작으로 얻기 위한 구조다.
- **중심 보기:** 선택 작업과 직접 연결된 작업의 부분 그래프를 같은 배치 함수에 넣어 재사용한다.
- **React Flow를 택하지 않은 이유:** 드래그 편집과 줌이 핵심 기능인데, 이 앱은 편집하지 않고 핀치 줌도 금지된다. 번들 비용에 비해 쓰는 기능이 적다.
- **dagre/ELK를 택하지 않은 이유:** 5~15개 작업에는 최장 깊이 배치로 충분하다. 기획서 12장의 포트폴리오 목적에도 직접 구현이 맞다.

### 8. 라우팅: React Router의 hash 라우터

`#/`, `#/projects/:id`, `#/projects/:id/tasks/:taskId`, `.../map`, `.../schedule`을 쓴다. 정적 번들에는 경로 재작성 서버가 없으므로 경로 기반 대신 hash를 쓴다. 브라우저 히스토리를 사용하므로 뒤로가기 동작이 히스토리에 맞춰 이어질 것으로 예상하지만, 실기기 확인 전까지는 가정이다.

### 9. UI와 프로젝트 구성

- TDS 컴포넌트를 기본으로 사용하고, 경로도만 직접 구현한다.
- `color-scheme: light`를 지정하고, 다크 모드 분기를 두지 않는다.
- 공식 절차대로 Vite 프로젝트를 구성한 뒤 `npx ait init`을 실행한다. 공식 문서에 `apps-in-toss.config.ts`와 `granite.config.ts`가 모두 등장하므로, 설정 파일명과 옵션은 실제 생성 결과를 따른다.
- 테스트는 Vitest로 `domain/`과 `storage/`를 검증하고, 화면은 브라우저와 실기기에서 검증한다.

### 10. 기획서에 없어 임의로 정한 규칙

아래는 기획서에 명시되지 않아 기본값으로 정했으며, 검토 시 바꿀 수 있다.

| 항목 | 정한 값 |
|---|---|
| 대기 중 작업의 상태 변경 | 거부 |
| 선행 작업 완료 취소 시 후속 작업 | 상태 유지, 경고만 표시 |
| 중간 작업 삭제 시 | 후속 작업이 선행 작업을 상속하지 않음 |
| 작업·프로젝트명 길이 | 1~50자 |
| 예상 기간 범위 | 1~999 정수 |

### 11. 테스트용 샘플 프로젝트

앱 안 테스트에서 작업을 매번 입력하지 않도록 프로젝트 홈에 샘플 프로젝트 추가 버튼을 둔다. 데이터는 `domain/sample`이 기존 `domain/mutations`를 거쳐 만들므로 입력 검증과 순환 차단을 그대로 통과한다. 기존 데이터를 덮어쓰지 않고 프로젝트를 추가하며, 지울 때는 일반 프로젝트 삭제를 쓴다.

- **표시 조건:** `import.meta.env.DEV` 또는 `VITE_SAMPLE_DATA=true`. 일반 빌드에는 버튼이 없고, 토스앱 실기기 테스트에서는 이 값을 지정해 빌드한다.
- **데이터:** 대표 시나리오 4개 작업(기획 3일, UI 제작 5일, API 개발 7일, 통합 테스트 2일)을 쓴다. 표시 상태 네 가지와 핵심 경로, 여유 기간이 한 프로젝트에서 모두 나타난다.
- **첫 실행 자동 주입을 택하지 않은 이유:** 저장된 실제 데이터와 섞이거나 삭제 후 다시 생기지 않도록 사용자가 누를 때만 추가한다.

### 12. 화면 친절성 개선 (구현 전 계획)

**상태:** 구현 전이다. 코드는 아직 바뀌지 않았다. 화면 구성은 2026-11-04 사용자가 전체 적용을 선택했고, 문구는 아래 표를 사용자가 확인한 뒤 적용한다. 구현 항목은 `tasks.md` 7장이 관리한다.

**배경:** 실기기 테스트에서 사용자가 "기능은 정상이지만 디자인이 너무 불친절하다"고 평가했다. 화면과 코드에서 찾은 원인은 다음과 같다. 사용자가 항목별로 지목한 것은 아니며, 실기기 화면은 직접 보지 못했다.

| 원인 | 현재 |
|---|---|
| 할 일이 잘 안 보임 | 프로젝트 상세에 같은 작업이 두 번 나오고, 모든 카드에 드롭다운이 있어 폭 360px에서 약 4화면 길이다 |
| 다음 행동이 불분명함 | 상태를 바꾸려면 드롭다운을 열어야 하고, 경로도·일정 분석으로 가는 길이 카드 사이의 작은 글자 링크뿐이다 |
| 상태가 눈에 안 띔 | 상태가 평범한 글자로만 표시된다 |
| 용어가 어려움 | `핵심`, `여유 기간`, `선행 작업`을 설명 없이 쓴다 |
| 글자가 작고 탭할 곳이 모호함 | 경로도와 일정 분석에 12~14px 글자가 있고, 목록에 이동 표시가 없다 |

**변경하지 않는 것:** `domain/`, `storage/`, `state/`의 동작과 저장 형식. 대기 중 작업의 상태 변경 거부와 완료 취소 규칙도 그대로다. 달라지는 것은 상태를 바꾸는 위치와 화면 표현뿐이다.

#### 화면별 구성

| 화면 | 위에서 아래 순서 |
|---|---|
| 프로젝트 홈 | 제목 → 프로젝트 카드(전체 탭 가능, 진행률 막대, 상태별 작업 수) → `프로젝트 추가` → 데이터 보관 안내. 빈 상태에는 설명과 `프로젝트 추가`를 함께 둔다 |
| 프로젝트 상세 | 프로젝트명 → 진행률 막대와 완료 수 → `경로도`, `일정 보기` → 다음 할 일 카드 → 기다리는 작업과 사유 → 전체 작업(한 줄 목록) → `작업 추가` → 프로젝트 수정·삭제 |
| 작업 편집 | 입력 항목과 도움말 → 저장·취소 → 기존 작업이면 상태 변경과 삭제 |
| 경로도 | 제목 → 한 줄 안내 → 범례 → 그래프 → 선택한 작업 정보 |
| 일정 분석 | 요약 숫자 → 일정을 좌우하는 작업 → 작업별 일정 → 계산 안내 |

#### 상태 변경 위치

- 프로젝트 상세의 다음 할 일 카드에는 버튼을 하나만 둔다. 시작 가능이면 `시작하기`(진행 중으로), 진행 중이면 `완료하기`(완료로) 버튼이다.
- 대기 중 작업에는 상태 버튼을 두지 않고 먼저 끝낼 작업을 보여준다.
- 시작 가능 작업을 바로 완료로 바꾸거나 완료를 취소하는 등 나머지 변경은 작업 편집 화면에서 한다. 상태 변경은 저장 버튼과 별개로 누르는 즉시 반영한다.
- 다음 할 일 카드의 작업은 전체 작업 목록에도 한 줄로 다시 나오지만, 상태 버튼은 카드에만 있다.

#### 시각 규칙

- `app.css`의 CSS 변수에 색, 글자 크기, 간격을 모으고 화면의 고정값을 대신한다. 값은 AIT `design` 스킬의 중립 토큰을 출발점으로 삼되, 강조색은 브랜드 색 `#0F766E`을 쓴다.
- 현재 앱이 직접 지정한 파란색(링크 `#1760bc`, 진행 중 `#3182f6` 계열)은 토스 브랜드 색과 혼동되지 않도록 브랜드 색 계열로 바꾼다. TDS 버튼은 그대로 쓴다. SDK 코드상 토스 앱에서는 설정한 브랜드 색을, 일반 브라우저에서는 파란색 기본값을 쓴다. 실기기 색은 아직 미확인이다.
- 글자는 본문 15px 이상, 메타 정보 13px 이상으로 하고 11px 이하는 쓰지 않는다. 강조는 굵기와 색으로 하며 `font-weight`는 400~700만 쓴다.
- 누르는 요소는 44px 이상으로 한다. 목록의 이동 표시는 글자가 아닌 SVG 꺾쇠를 쓰고, 버튼 안에는 넣지 않는다.
- 상태는 공통 배지 하나로 표시하며, 글자가 항상 함께 나온다. 작은 글자의 명도 대비는 구현 후 4.5:1 이상인지 측정한다.
- 상단 내비게이션은 그리지 않는다. 하단 고정 버튼도 추가하지 않아 safe area 값을 새로 쓰지 않으며, 화면 끝에 여백만 둔다.
- 경로도는 2열까지 폭 320px에서 가로 스크롤 없이 보이게 하고, 3열 이상은 기존처럼 스크롤한다. 노드의 작업명은 15px, 상태 줄은 13px 이상으로 하며 노드 크기는 이에 맞춰 조정한다. 도메인의 기본 배치값은 바꾸지 않고 화면에서 넘기는 옵션만 조정한다.

#### 검증 계획

- `npm run typecheck`, `npm test`, 일반 빌드와 `VITE_SAMPLE_DATA=true` 빌드의 버튼 유무.
- 개발 서버 폭 320px, 360px에서 다섯 화면과 빈 상태·오류 상태를 캡처로 확인한다. 가로 넘침, 텍스트 겹침, 글자 크기 전수, 터치 영역, 명도 대비를 측정한다.
- 대표 시나리오를 다시 수행해 시작하기·완료하기, 완료 취소, 대기 중 거부, 삭제, 새로고침 후 복원이 그대로인지 확인한다.
- 작업 15개 샘플로 경로도를 확인한다. 기존 task 5.5의 수행 기록을 찾지 못했으므로 이때 함께 기록을 남긴다.
- AIT `design` 스킬의 품질 기준(G0~G8)으로 화면별 판정을 남긴다.
- 테스트 번들로 토스앱에서 사용자가 최종 확인한다. 정적 검사와 브라우저 결과만으로 실기기 표시를 확인했다고 보지 않는다.

## Risks / Trade-offs

- **[상태 변경 위치 이동으로 조작 단계가 늘어남]** → 자주 쓰는 시작·완료는 상세에서 버튼 한 번으로 끝내고, 드물게 쓰는 완료 취소만 작업 편집으로 옮긴다. 다음 할 일에 없는 완료 작업은 목록에서 작업을 눌러 들어간다.
- **[출시 빌드에 샘플 버튼이 포함될 수 있음]** → 같은 터미널이나 `.env` 파일에 `VITE_SAMPLE_DATA=true`가 남아 있으면 포함된다. 출시 빌드 전에 값을 지우고 번들에 버튼 문구가 없는지 확인한다.

- **[기기 변경·앱 삭제 시 데이터 유실]** → 로그인과 서버가 범위 밖이므로 막을 수 없다. 앱 안에서 보존 조건을 안내한다.
- **[식별키와 로컬 데이터는 연결되지 않음]** → 식별키는 앱 시작 시 확인·저장만 하며 데이터 복구나 계정별 분리에 쓰지 않는다. 같은 기기의 계정 변경 처리는 MVP 범위 밖이다.
- **[`Storage` 용량 제한이 문서에서 확인되지 않음]** → 소규모 데이터라 초과 가능성은 낮다고 본다. 쓰기 실패는 저장 실패 안내로 처리한다.
- **[층을 건너뛰는 연결선이 노드 뒤를 지나 읽기 어려움]** → 소규모 그래프에서 허용하고, 선택 작업 중심 보기로 보완한다. 15개 작업 샘플로 확인한다.
- **[직접 구현한 배치의 품질이 라이브러리보다 낮을 수 있음]** → 배치 함수를 분리해 두어 교체 비용을 작게 유지한다.
- **[TDS가 일반 브라우저에서 제한적으로 동작할 수 있음]** → 도메인 로직은 TDS와 무관하게 테스트한다. 화면 표시는 개발 서버와 토스앱에서 확인한다.
- **[iOS 미검증]** → 검증 기기는 Android뿐이다. `user-scalable=no`와 뒤로가기의 iOS 동작은 확인 대상이 아니므로 결과 보고에 미검증으로 남긴다.

## Open Questions

- **TDS 사용 의무:** 필수 여부를 확정하지 못했다. TDS를 쓰기로 했으므로 이 설계에는 영향이 없다.
- **이모지 서체:** 고정 문구에는 이모지가 없지만 사용자가 입력한 작업명에는 들어갈 수 있다. AIT `design` 스킬은 Tossface를 요구하고, CDN 방식은 오프라인 사용 요구와, 번들 방식은 번들 크기와 충돌할 수 있다. 12장 구현 전에 적용 여부를 정한다.
- **실기기 버튼 색:** 토스앱에서 TDS 버튼이 브랜드 색으로 나오는지 사용자 확인이 남아 있다.
